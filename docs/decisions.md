# Design decisions and measurements

Material moved out of the [system design](system-design.md) to keep it readable: the measurements behind allocation choices, and the full session-revocation and auth-cookie design.

## Best fit vs first fit

Both allocators work under the same bay-fit rules; a "regret" is a refusal an offline re-assignment would have fitted.

| Streams | Engine (labour min / refusals / regrets) | First fit | Test |
|---|---|---|---|
| 24 fixed random streams | 9600 / – / 2 (+6.3 %) | 9030 / – / 6 | `TestAllocationRegretNoWorseThanFirstFit` |
| 24 streams, half waiters | 10710 / – / 1 (+3.5 %); without the repair 10440 / – / 3 | 10350 / – / 5 | `TestAllocationRegretWithWaiters` |
| 400 streams | 157380 / 3100 / 19 | 152400 / 3135 / 83 | `TestEngineRegretWide` (`ENGINE_REGRET_SEEDS=400`) |
| 400 streams, half waiters | 165630 / 3022 / 31 | 158250 / 3075 / 111 | same |

Alternatives tried:

- **Least-loaded, most senior technician for waiters** (the customer is in the lounge): the same on the 24 streams, but over 400 streams with half waiters 164970 minutes and 33 regrets vs best fit's 165630 and 31 — spreading waiter jobs fragments the timelines and spends the senior technicians a later major needs. The former least-loaded order for everyone sat between first fit and best fit.
- **Dropping load as the last tie-break:** no change (157380, 19).
- **Unrestricted technician moves in the repair:** fewer refusals but fewer minutes booked on the plain streams (moving work onto the only senior technician turned a later major away), hence the "no scarcer" rule.

## Engine measurements

**Measured: fragmentation-aware best fit (not adopted).** Ranking bays and technicians first by *dead* minutes — a side gap shorter than the shortest job that resource can take (a technician's shortest service they are qualified for; a general bay 30, the express spill; an express bay its shortest express job), which nothing could ever fill — and only then by the total idle time, consistently in allocation, the repair, and the hint, changed nothing measurable: `TestAllocationRegretNoWorseThanFirstFit` 9600 min / 2 regrets and `TestAllocationRegretWithWaiters` 10710 / 1 either way, over 400 streams 157380 min / 3100 refusals / 19 regrets and (waiters) 165630 / 3022 / 31 either way, `TestQualityDayBeatsEveryFirstFit` 960 of 960 either way, `TestTechnicianBestFitKeepsLongStretch` passing either way. On the 30-minute grid bays never have dead gaps (every bay takes a 30-minute job), and two technicians rarely tie on level and spare skills while differing in dead minutes; the plain total stays (`store.fitRankSQL`).

**Measured: when a booking reads its candidates under the day lock.** Reading after the vehicle + dealership-day locks makes the read exact (nobody collides and re-reads under the lock), but serialises the reads of one day's bookings even when they want different bays and technicians; and it once meant a booking checked its technician (`FOR SHARE`) under the day lock, so one waiting behind a roster edit (technician `FOR UPDATE`, up to `lock_timeout`) stalled every booking of that dealership-day (`TestRosterEditDoesNotStallOtherBookingsInTheWindow`). Now every booking's first pass takes the locks with its candidate read inside a savepoint: it *waits* for the day lock when its day is contended — its instance's gate saw others of the day, or a booking of that dealership collided on this instance within the last second (`booking.hotDealers`: another instance's contention shows up as collisions, so no shared state is needed) — and otherwise only *tries* it (free: exact read, and one round trip less than taking it last; busy: stale read, lock taken right before the insert, as before). Holding the day lock in that savepoint, technicians are checked `FOR SHARE SKIP LOCKED` (then the roster in a fresh snapshot, as always); one under a roster edit (a candidate, or the one-move repair's target) makes the booking roll the savepoint back — the day lock with it — wait for that technician's share lock outside the day's queue, and book again, so it ends with the technician it would have got anyway and the day does not stall (`TestRosterEditNeverHoldsTheDayLock`, `TestRosterEditDuringBurstOneWinner`, `TestRosterEditOnRepairTargetNeverHoldsTheDayLock`; after three such give-backs the last pass is plain lock-last). DB benchmark, booking.Service on Postgres with an instance per worker, 10 workers, 1600 oil changes, medians of 5 interleaved runs (`BenchmarkBookSameDayAcrossInstances`, `BenchmarkBookUncontended`, ms per booking): same slot across instances 4.25 → **2.39**; same day, different slots 1.33 → 1.36 (noise level); uncontended (one instance, every booking another day) 1.06 → **0.98**. Waiting for the day lock on *every* booking instead (what was measured first) gives 2.25 / **1.98** / 0.98: the same-slot win, but 49 % slower for same-day bookings of different slots, whose reads it serialises — not adopted.

## Session revocation

`users.token_version` in every token; logout (Bearer or refresh cookie) bumps it (all tokens and WS tickets stop working), revokes every refresh session of the user in the same TX, and emits `SESSION_REVOKED` with the new token version so every instance closes the user's sockets opened before it (a late or replayed revoke spares newer sessions); at most 10 sockets per user per instance (an extra handshake gets HTTP 429 + `Retry-After`, not an upgrade); each hub re-checks active/role/customer/dealership/version and the session of all its sockets in one batched query about once per ping period (jittered); refresh rotation locks the user row then the token row in one TX, so two refreshes of one token rotate once (the later one, within the grace, gets an access token and the same, deterministically derived successor cookie) and a refresh never survives a concurrent logout or a login replacing its family; refresh-token reuse (a rotated token past the grace) takes the logout path (revoke all, bump, `SESSION_REVOKED`), while a token of an already revoked session is only refused; access tokens and sockets carry their session (`sid`), so a revoked session (a new login replacing it) ends them too — `requireAuth` reads the session's liveness with the user (one query, cached for `USER_CACHE_TTL`) and the hub's sweep checks it in its batched query; a socket lives until the session's absolute end (`sexp`), not the 15 min access token

## Auth sessions and CSRF

bcrypt passwords, HS256 JWT with audiences (`api` access token, 15 min by default, carrying the session id `sid` and its absolute end `sexp`; 60 s `ws` ticket), opaque 256-bit refresh tokens (only their SHA-256 is stored, `auth_sessions`) rotated on every `POST /auth/refresh` in an `HttpOnly; SameSite=Strict` cookie (`__Host-uss_refresh` on `/` with `Secure`, else `uss_refresh` on `/api/v1/auth`; a duplicate is refused, never one picked): idle 24 h, absolute 7 days, 60 s grace for racing tabs or a lost response (the same successor is sent again), reuse after it revokes every session of the user (expiry is checked first: an expired token is only refused); cookie endpoints require `X-Requested-With: fetch` and a same-origin `Origin`, login/register a JSON `Content-Type`, every auth write a `Sec-Fetch-Site` other than `cross-site` (CSRF); all session times on the database clock

Rate limits and Redis: Redis idempotency (id + fingerprint, per user), rate limiting (login per client IP + email in one round trip; register per IP and cluster-wide; refresh per IP; customers' plain reads, availability and booking writes; WS tickets per user; staff customer search and create; one Lua script checks every bucket and counts only when all have room, so a refused request never drains a shared per-IP or cluster-wide bucket; emails appear in keys only as a keyed HMAC pseudonym) and single-use WS tickets — every call bounded by a 100 ms fast-path timeout and failing open, except the login/register limits, which fall back to a bounded per-instance memory limiter while Redis is down; a 429's `Retry-After` is the exceeded window's remaining TTL (read in the same round trip). The server starts with Redis down (readiness `degraded`) unless `REDIS_REQUIRED=true`
