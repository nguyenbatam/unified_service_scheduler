# Backend rules (Go)

These invariants override generic Go skill advice (notably `golang-database`). Rationale: `docs/PLAN.md` §0.2, §4.1.

## Booking invariants

1. One confirmed appointment = 1 bay + 1 qualified, on-duty technician over half-open `[start, end)`, for 1–5 job lines (`appointment_lines`): the technician holds every line's skill at the highest `min_skill_level`, the bay fits every line (express < general < one specialty; diagnostic + alignment cannot share), the window is the summed labour time (`booking.Combine`). Lines and requirements are a **booked snapshot** on the row (`booked_duration_minutes`, `required_bay_type`, `required_skills`, `min_skill_level`); catalog edits never rewrite existing bookings.
2. **Double-book guarantee is PostgreSQL**: `EXCLUDE USING gist` on `tstzrange(start_at, end_at, '[)')` for bay, technician, and vehicle, only for holding statuses `1|2|3`. Never replace or "optimise away" this with app-level locks. Map violations by constraint name (`store.ExclusionConstraint`).
3. `SELECT … FOR UPDATE` on bay/tech rows is **not** sufficient for interval overlap; Redis/Redlock is never the source of truth.
4. Exclusion violation → `store.IsExclusionViolation` → domain `conflict` (409). Do not retry silently.
5. **Idempotency**: keys are scoped per creating user — unique index `(created_by, idempotency_key)` checked inside the booking TX after the per-key advisory lock (`Tx.BookingInputs`: the lock and the lookup lead its batch, before the dealership `FOR SHARE`, so a retry racing its own original replays instead of colliding); Redis caches only `{id, fingerprint}`, is skipped on error, and replays re-read Postgres. Same user + key + payload → replay 200; different payload → 409. A replay (Redis or Postgres path) is an appointment read: it re-checks `actor.CanAccessAppointment` first and is 404 once the appointment is outside the actor's scope.
6. **Multi-instance**: backends hold no booking state; shared Postgres is the truth. Changes to booking/read paths must still pass `scripts/smoke_cluster.sh` (book on A, read on B).
7. **Events**: every appointment change calls `Tx.RecordAppointmentEvent` in the **same TX** (`InsertAppointmentWithEvent` writes the created event in the insert's own pgx batch, payload built in SQL by `store.appointmentPayloadSQL`; keep it in step with `domain.Appointment`'s json tags — `TestCreatedEventPayloadMatchesAppointment`) — one `outbox_events` row plus one `appointment_history` (audit) row with the acting user (sweeps use the set-based `Tx.RecordAppointmentEvents`: same rows, one statement, each appointment locked first). Never publish to Kafka or the WS hub directly from a request. The workers are woken **after** COMMIT, never by a `pg_notify` inside the TX (its commit takes a cluster-wide lock and would serialise every booking's COMMIT, staging/day lock included): a `Tx` that wrote outbox rows (`Tx.markEvents`, shared with its savepoints) signals on a successful top-level `Tx.Commit` — the local worker directly (`Store.OutboxWakeups`), the other instances through `Store.RunOutboxNotifier` (one autocommit NOTIFY per burst, best effort; every worker's poll covers a lost one). Worker → Kafka → every instance's WS hub (per-boot consumer group `events.FanoutGroupID`, starts `FromLatest` so a restart never replays; it still commits, because kafka-go re-reads committed offsets at every rebalance and an uncommitted group would jump to the end and drop events, `SESSION_REVOKED` included; `DeleteGroupOnClose` removes it on shutdown, a crashed boot's group expires via `offsets.retention.minutes`) and the notifier (one shared committed group `scheduler-notify`, starts `FromEarliest`: replay is safe via `dedupe_key`). The fan-out consumer decodes with `events.SkipPayload()` (the PII payload is never decoded on the hub path). Handler panics are recovered (`events.PanicError`; `Chain` recovers per member): an event whose handler fails only by panicking is tried `maxHandlerPanics` (5, doubling backoff from 250 ms, ~3.75 s) times, then logged, counted in `scheduler_events_skipped_total` (alert `EventsSkipped`, page) and skipped/committed like an undecodable message; ordinary errors are still retried until they succeed. **Per-aggregate order**: rows carry `seq`, drawn at insert (after the aggregate's row lock, so in commit order — never order by `created_at`, which is the TX start); `ClaimOutbox` claims an aggregate's events in `seq` order (across aggregates oldest-due first: `next_attempt_at`, then `seq`) and never claims a row while an older row of the same aggregate is `pending` or any row of it is `processing` (a requeued failed row is older than events published after it), so one aggregate has one event in flight (the one narrow exception: a claim whose snapshot predates a requeue may take a newer event while another claims the requeued one — harmless, since a requeued event is late by definition and consumers ignore stale versions) and a retried event is never overtaken. For rows queued behind a head, `next_attempt_at` is only a cost hint that keeps them out of the claim's scan (`outbox_events_ready_idx`): the claim holds back never-claimed rows behind the heads it takes (`store.OutboxInflightHold`), a backed-off head pushes its queue up to its own retry time, and a resolved head (published, failed, poisoned) releases the next row; none of these ever lowers a claimed row's own backoff (attempts > 0) or delays a row past its predecessor. Kafka keys by aggregate id (one partition). Only per-message **content** rejections (message too large, invalid/corrupt record; `events.Bus` resends a rejection shared by a partition batch one message at a time to pin it) count toward `rejections`/`failed`; transient errors (whole-batch or per partition, `events.RetriableError`) only back off. A `failed` row no longer blocks its aggregate, so later events go out and the failed one is lost to consumers until an operator requeues it (it then arrives late; consumers ignore stale versions) through the group-admin-only `GET /api/v1/admin/outbox/failed` and `POST /api/v1/admin/outbox/requeue` (authorised in `booking.Service`, `booking/outbox_admin.go`; `store.RequeueFailedOutboxIdle` skips an event while its aggregate has another one `processing`, and locks only pending rows, in id order like the marks, so it never deadlocks with them). Every mark (published, retry, poison) is fenced by `status` = processing AND `claimed_at`. Publishing ignores shutdown cancellation and is bounded instead: `OutboxConfig.Validate` keeps publish deadline (taken just before the claim, so it also covers the bounded claim) + `events.MaxWriteLifetime` (kafka-go retries a batch after the call returns) and + bookkeeping inside the lease, and rows whose publish outcome is unknown wait out `MaxWriteLifetime` before they can be claimed again, so a stale batch never overtakes a retry. `MaxWriteLifetime` holds for one kafka-go batch per partition per call: the writer's `BatchSize`/`BatchBytes` are explicit (`events.WriterBatchSize`/`WriterBatchBytes`), `Validate` refuses an outbox `BatchSize` above `WriterBatchSize`, and `events.Bus` splits a call that would exceed either into consecutive calls. Shutdown waits `drainBudget` (cmd/server: the longer of `OutboxConfig.DrainTimeout` and `notify.Config.DrainTimeout`, plus margin; `notify.Config.Validate` keeps a batch's send deadline, also taken before its claim, plus bookkeeping inside the lease) for in-flight work, and the compose `stop_grace_period` (40 s) must stay above it plus the deferred closes (`cmd/server` tests read `docker-compose.yml`). Kafka commits ignore shutdown cancellation (bounded by a short timeout), so a message handled just before shutdown is not redelivered.
8. Slot grid 30 min. Every enum-like column is `SMALLINT` (codes from 1, so Go's zero value is never valid) ↔ a Go `int16` type in `internal/domain`, its single definition: status, bay, skill, skill level (`domain.SkillLevel`, `1 apprentice … 4 master`), role (`domain.go`) and event type, aggregate type, notification kind/channel, outbox and notification status (`codes.go`). SQL in Go never spells a code as a bare number: `store/codes.go` derives the literals from those constants (`statusConfirmedSQL`, `holdingSQL`, `outboxPending`, …) and queries concatenate them (literals, not parameters, so partial indexes still match); JSON carries the numbers too (the notification webhook alone sends names, for a third-party gateway). Only `001_schema.sql` writes numbers (CHECKs, GiST and partial-index predicates), with the names in comments. Codes: status `1 confirmed, 2 checked_in, 3 in_progress, 4 completed, 5 cancelled, 6 no_show`; bay `1 express, 2 general, 3 diagnostic, 4 alignment`; skill `1 lubrication, 2 brakes, 3 general`. Appointment bounds are `timestamptz`; open/close/lunch are `time`.
9. Holding statuses `1|2|3` occupy bay+tech+vehicle; `4|5|6` release them. Lifecycle is `confirmed → checked_in → in_progress → completed`; cancel from `1|2`; `no_show` (6) from `1` after start; `reinstate` (6 → 2) before the booked end, re-held under GiST, re-checking — over the part of the kept booked window still ahead of now, like the config guards — the technician (`LockBookableTechnician`), the day's calendar (closure, hours, lunch — read after the dealership `FOR SHARE`: config changes only refuse to strand holding appointments, so they may have changed since the no-show), and the arrival window's staging room. check-in is allowed from the appointment's local day until its booked end (afterwards 422: reschedule); `start` refuses while the technician or bay still has another job in progress; starting **before** the booked start, or **after** the booked window has ended, moves the window to `[now, now+length)` under GiST (the car is on site: staging, lunch, and roster are not re-checked for it). **Reschedule is in place** (same id, version bumped, `scheduled_at` reset when the start changes; a change of only the waiter flag keeps the window and is recorded as `APPOINTMENT_REASSIGNED`, so no "moved" notice), keeps the booked snapshot (never re-priced from the catalog), and excludes its own hold from every check — availability does the same when given `excludeAppointmentId` (authorised like a read, same dealership + vehicle, and refused like the move itself: 409 unless confirmed, 422 for a customer past the change cutoff); a same-start retry replays, a stale If-Match is 412. **Extend** (staff, status `2|3`): GiST and the 24h span always; for checked_in (not yet started) the part of the longer window `[start, end+by)` still ahead of now is re-checked like a booking (technician via `LockBookableTechnician` against the booked snapshot, then the day's calendar — closure, hours, lunch — after the dealership `FOR SHARE`), 422 otherwise; only the part ahead of now, like the config guards, so an edit that only touches the window's past never refuses it. In-progress work is an overrun and is not re-checked. **Reassign** (staff, status `1|2`) changes bay and/or technician in the same window: technician re-checked with `LockBookableTechnician` against the booked snapshot over the part of the window still ahead of now (nothing ahead: on duty now), bay must fit the booked type (`BayFits`), and neither target may be held by flagged overrunning work that started before the window ends (it holds until completed) (`Tx.OverrunHolds`, also checked by Reinstate on its booked bay and technician; an early start is covered by `LockWorkStart`, which refuses while either has any job in progress). The HTTP extend requires If-Match (428 `precondition_required` without it or with `*`): its body is a delta, so a blind retry would extend twice. Check-in and an on-time start take the dealership-day lock (`booking.lockHoldDay`): status is in the GiST predicates, so they write new entries and could deadlock with a booking inserting from stale candidates. An appointment never spans more than 24h (`appointments_max_span`; day-window queries — the day board (`Store.ScheduleBoard`) and availability's dealership and vehicle holds (`Store.AvailabilityRange`) — rely on it as a lower bound on `start_at`). Every appointment change bumps `version` and goes through `booking` (row lock → scope/ownership → If-Match → state check).
10. Allocate only techs with every required skill, `skill_level >= min_skill_level`, and **on duty** (`technician_shifts` weekly pattern + break, `technician_absences`; no pattern = opening hours), re-checked under `Tx.LockBookableTechnician` right before insert — on the booking TX, not inside a candidate's savepoint (a savepoint rollback would release the row lock), so the result is cached per technician across bays. That check is two statements on purpose: `FOR SHARE` on the technician row, then the roster check in a fresh snapshot (READ COMMITTED re-checks only the locked row after a wait; subqueries would read the old snapshot). They are pipelined in one pgx batch, which keeps that property: the server runs the second only after the first (lock wait included) and each statement takes its own snapshot; never merge them into one statement. Roster writers lock the technician `FOR UPDATE`. The SQL on-duty rule (`store.technicianOnDutySQL`) and its Go twin for availability (`booking.roster.onDuty`) must stay in step. `cmd/stress` keeps its own, deliberately independent copy of the duty, job-line, and soft-upgrade rules (`cmd/stress/rules.go`, its oracle and integrity pass): never make it import the engine's, or a bug shared by both passes unseen; change it when the documented rules change. Both compare local wall-clock times of day and dates, never instants built with `time.Date` (a boundary inside a DST gap would otherwise drift by an hour); the calendar rules do the same (`booking.dayClocks.withinHours`/`crossesLunch` mirror `Tx.refuseStranded`). Dealership rules are read FOR SHARE in the booking TX so admin changes cannot interleave; service types are a plain read (the booking snapshots its lines and requirement and catalog edits apply to new bookings only, so a share lock would only make every booking in the group lock the same catalog rows and stall behind a group admin's edit). **Lock order** (keep it acyclic; documented on `booking.allocate`, whose per-pass state across candidate rounds is `booking.placement` (one per `placeOnce`; a give-back starts a fresh one), `booking/allocate.go`): appointment row `FOR NO KEY UPDATE` (reschedule/reinstate/reassign/extend/transitions/sweeps: ids never change, and unlike `FOR UPDATE` it does not block the foreign-key KEY SHARE of the notifier's inserts) or idempotency advisory lock (book) → the share locks (dealership, technician; their relative order is free since share locks never conflict with each other) → vehicle advisory lock → **dealership-day** advisory lock (the dealership's local day of the hold, key derived in SQL from its timezone: `store.dealershipDayLockSQL`) → GiST writes. The vehicle + day locks (`Tx.LockArrival` via `booking.claimStagingRoom`, one round trip; `Tx.LockDealershipDay` for reassign, extend, check-in, a start (early or on time; StartWork first takes its `start|tech` / `start|bay` advisory locks, `Tx.LockWorkStart`, then the day lock), and the overrun sweep, which change holds in place; a hold that may run past local midnight locks its end's day too, and a reschedule to another local day also locks the day it leaves (`store.ArrivalLock.Leaving`: its move rewrites a GiST entry there; `TestCrossDayReschedulesLockBothDays`) — several days are always locked in ascending day order, `ArrivalLock.days`) are taken even when the dealership has no staging cap: they queue every writer that could collide — bays and technicians belong to one dealership and the holds of one dealership-day are queued together — because concurrent GiST writes over overlapping windows otherwise wait on each other's uncommitted entries (even across constraints: bay vs technician) and deadlock, which Postgres breaks one per `deadlock_timeout` while everyone queued behind runs into `lock_timeout` (503). A lock per staging window was not enough: overlapping jobs arriving in different windows deadlocked (`TestOverlappingBookingsOfOneDayNeverDeadlock`). Other days and dealerships stay parallel; GiST stays the guarantee. A booking's first pass takes the vehicle + day locks in the round trip that reads its candidates, inside a savepoint it can give back (`Tx.LockArrivalAndCandidatesRevocably`, `alloc_day`: rolling a savepoint back releases the transaction-level advisory locks taken in it), waiting for the day lock when the day is contended (`allocation.lockFirst`, below) and otherwise only trying it (`ArrivalLock.Try`, single-day holds: free → the read is exact at no extra round trip; busy → the read is stale and the day lock is waited for right before the first insert, lock-last, holding only the vehicle lock meanwhile). While it holds the day lock in that savepoint it never waits for a technician (candidate or the repair's target): the check is `NoWait` (`TechCheck.NoWait`: `FOR SHARE SKIP LOCKED`, then the same fresh-snapshot roster statement), a technician a roster writer holds returns `store.ErrTechnicianLocked`, and the pass rolls the savepoint back (undoing any repair move), waits for that technician's share lock on the TX itself (`Tx.ShareLockTechnician`, outside the day's queue: share locks precede the vehicle and day locks in the order) and places the booking again (`booking.allocate`; the share lock holds until the TX ends, so that technician cannot stall the next pass) — so a roster edit never stalls the dealership-day, and the outcome is the one waiting for the technician gives (no technician is passed over for being mid-edit; `TestRosterEditNeverHoldsTheDayLock`, `TestRosterEditDuringBurstOneWinner`, `TestRosterEditOnRepairTargetNeverHoldsTheDayLock`, `TestGiveBackUndoesAnAppliedRepairMove`, `TestGiveBacksBoundedThenPlainPass`). Only a plain lock-last pass — after `maxGiveBacks` (3) give-backs, i.e. that many technicians the booking needs under concurrent roster edits, or for a cross-day hold that is not lockFirst — may still check a technician after the day lock (a later candidate, the repair's target), and any pass one while holding only the vehicle lock; both are safe because the exclusive lockers (admin config, roster writers, deactivation) hold one row and never wait for a vehicle/day lock, an appointment row, or a GiST entry afterwards. The first candidate's SAVEPOINT is opened in the same round trip as the locks (`ArrivalLock.Savepoint`; its Rollback also releases it, so later technician checks run on the TX itself), and after the first GiST collision the candidates are re-read once under the day lock (exact then: no other booking of that day can commit, `placement.reread`), so a loser fails at once instead of trying every stale candidate while everyone waits — except that when that re-read finds nothing free it still tries the one-move repair once (if it has not repaired yet) before the 409, as availability and a retry would (`TestLostRaceStillMakesRoom`). Per instance, at most `dayGateWidth` bookings and reschedules of one dealership-day are let into the database at once (`booking.dayGate`, before `Store.Begin`, keyed on the dealership's **local** day like the database lock — timezones come from a per-instance cache, `Service.gateKey`, never stale since a dealership's timezone cannot change; a reschedule reads its dealership and timezone first, `Store.AppointmentDealership`): the rest wait in memory, bounded by their request deadline, instead of pinning pool connections behind the day lock. Staff-only writers (reinstate, extend, reassign, early start) are not gated: rare, and the extra round trip is not worth it. A booking or reschedule **waits** for the vehicle + day locks before reading its candidates (`allocation.lockFirst`; each read is its own statement queued after the locks in the same round trip, so its snapshot is fresh) when it met others of its day in the gate, or when a booking of that dealership collided on this instance within `hotMemory` (1 s, `booking.hotDealers`: per instance and only a hint — another instance's contention shows up here as collisions, with no shared state), so the read is exact and the ranking current; a day lock held (waited for or tried) opens each candidate's savepoint in the round trip of its technician check (`Tx.LockBookableTechnicianSavepoint`, queued after the share lock so a rollback keeps it). Otherwise it only tries the day lock, so same-day bookings that do not compete for the same bay or technician keep reading in parallel: waiting for it every time halves same-slot contention across instances but serialises those reads (measured, `docs/decisions.md#engine-measurements`). **One-move repair** (`booking/repair.go`, `store/repair.go`): when nothing free is read for a slot (no bay, no technician, or neither), the booking may move ONE confirmed (status 1), not yet started (`start_at > now`) appointment that is the only hold of a fitting bay (technician) in the slot to another bay that fits its booked requirement (`bayFitsSQL` with its own waiter upgrade) or another technician qualified, on duty, and no scarcer for it (level and spare skills no higher than the one it leaves), same window, free and not overrun-held — at most one move per resource; the moved row gets `APPOINTMENT_REASSIGNED` + history (actor: staff booker, else system). Moves only under the dealership-day lock (an uncontended booking first probes without locks, `Tx.RepairPossible`, then takes the lock and re-reads), the staging cap is judged before anything moves, the moved row is locked `FOR NO KEY UPDATE SKIP LOCKED` — the one lock taken after the day lock on an appointment row, and it never waits (a writer holding that row may be queued for the day lock: Reassign, Extend, check-in take row then day), and the target technician is re-checked with `LockBookableTechnician`. Availability offers a slot exactly when such moves exist (`availRange.bayRepairable`/`techRepairable`, Go twins of `store.bayRepairSQL`/`techRepairSQL`; keep them in step); `freeBays`/`freeTechnicians` stay the counts free without a move, so an offered slot may show 0. A GiST deadlock re-reads the candidates once, like a collision. A request TX never takes a second pool connection while it holds one (plain reads inside it use `Tx` methods such as `Tx.ReadDealership`), or a full pool deadlocks.
11. **Bay fit** (`booking.BayFits`, SQL twin `store.bayFitsSQL`; `cmd/stress/rules.go` restates it): the exact type; an **express spill** — any express job may use a free general bay, only as the fallback when no express bay is free (a general bay holds anything the quick lane does; ranked after express bays, best fit); and the **waiter** (`is_waiter`) soft-upgrade from `required_bay_type=2` to a free express bay, only when the job is ≤ the dealership's `express_max_minutes` (so long jobs never block the quick lane), and only as the **fallback**: bays of the required type are ranked first (express jobs can use nothing else, so the quick lane is never spent while a general bay is idle — `TestWaiterSoftUpgradeRacingOilChange`); non-waiter keeps the strict bay type (plus the express spill). The technician order is the same, waiter or not: lowest qualifying `skill_level`, fewest spare skills (beyond the job's), smallest idle gap on that technician's own day (the bookable stretch and their shift and break are edges), least loaded (booked minutes that day) — so senior and versatile techs stay free for work only they can do and long free stretches stay whole instead of being spread across every timeline (`store.freeTechniciansSQL`; `TestTechnicianBestFitKeepsLongStretch`, `TestAllocationRegretNoWorseThanFirstFit`, which judges the engine against a first-fit baseline with an offline oracle). Availability restates the ranking in Go, so keep each pair in step: `store.freeTechniciansSQL` order ↔ `booking.availRange.pickTech`, `store.sideGapsSQL` ↔ `booking.sideGaps`, `store.fitRankSQL` ↔ `booking.gaps.fit`, `store.techStretchSQL` ↔ `booking.roster.stretch`, and (repair) `store.movableSQL` ↔ `booking.movable`. Waiters once got the least-loaded, most senior technician instead; that fragmented timelines and spent the senior technicians the next major needs. Within each group (required type, then the express fallback) bays are ranked best fit (smallest idle gap to the neighbouring bookings inside the slot's bookable stretch — opening or the end of lunch to the start of lunch or closing, `store.Slot.Lo/Hi` from `booking.dayClocks.stretch`). Ranking is a pre-check only: flagged overrunning work (`status=3 AND overrun_at IS NOT NULL`) also counts as holding its bay and technician from its start until it is completed — a carry-over job, across days if need be — in the candidates and in availability (`store.overrunHeldSQL`, `queueConfirmedBusy`; keep them in step), while GiST stays the guarantee.
12. Enforce the day's calendar (dated closures, weekday overrides in `dealership_hours`, else dealership defaults — read in the booking TX after the dealership `FOR SHARE`), `staging_capacity` arrivals per `staging_window_minutes` window (`Tx.LockArrival`: the vehicle and dealership-day advisory locks — the window lies inside the day — then the count as a separate statement queued after them in the same round trip, so its snapshot is fresh; shared by Book, Reschedule, and Reinstate via `booking.claimStagingRoom`), and that day's lunch window before allocating (the day's calendar is read in the inputs batch right after the dealership `FOR SHARE`, `store.DayRulesAt`, falling back to `Tx.DayRules` when Postgres and Go disagree on the local day). No bookings in the past. Self-service rules are **per dealership** (`domain.Policy`: `customer_lead_minutes`, `customer_change_cutoff_minutes`, `booking_horizon_days`, `no_show_grace_minutes`, `express_max_minutes`); staff are bound by none of the customer limits.
13. **Authorization lives in `booking.Service`** via `domain.Actor`: customers only see/act on their own vehicles and appointments (404 otherwise); workshop transitions and the day board are staff-only. Staff are scoped to `users.dealership_id` (`Actor.CanAccessDealership` / `CanAccessAppointment`): other dealerships' appointments are 404, dealership-level calls 403; an admin with no dealership is group-wide, and only a group admin edits the shared service catalog or opens a dealership (`POST /admin/dealerships`); customers are group-wide like vehicles: any staff member may record a walk-in customer (`POST /customers`, no account; a name plus a phone or an email) and search them (`GET /customers?q=` over name, phone, email — the access log records the path only, never the query); bays and technicians are added by an admin of that dealership or a group admin (`POST /admin/dealerships/:id/bays`, `POST /admin/technicians`; adding capacity strands nothing, so no stranded check, but each emits `CONFIG_UPDATED` and a bay bumps the dealership's version). Do not rely on route middleware alone.
14. **Realtime never ships PII to browsers**: outbox payloads stay on Kafka; the hub sends `AppointmentNotice` to staff/owner and an anonymous `AVAILABILITY_CHANGED` to other customers. Scoped staff (`Session.Scope`) never get other dealerships' appointment events.
15. **Sessions are revocable**: access tokens are short-lived (`ACCESS_TOKEN_TTL`, default 15 min, 1 m–1 h) and carry the refresh family `sid` and its absolute end `sexp`; a login/register starts a refresh family (`auth_sessions`, `001_schema.sql`: one row per opaque 32-byte token, only its SHA-256 stored; idle `SESSION_IDLE_TTL` per token, absolute `SESSION_MAX_TTL` per family, never extended) in the refresh cookie (`HttpOnly; SameSite=Strict`; with `AUTH_COOKIE_SECURE`, the default, `__Host-uss_refresh` on `Path=/` with `Secure` and no `Domain` — no cookie tossing — else `uss_refresh` on `Path=/api/v1/auth`; only the configured name is read and two of it are 401 + clear, never one picked), revoking the family of a cookie the request carried (and dropping it from this instance's family cache). `POST /auth/refresh` (`store.RefreshSession`) rotates in one TX: the user row `FOR NO KEY UPDATE` first (the same lock logout's token_version bump takes, so a successor committed by a refresh is always seen by a concurrent logout's revoke, and a refresh queued behind a logout reads its revoked row), then the token row `FOR UPDATE`; the successor token is derived from the presented one (`auth.SuccessorRefreshToken`, HMAC under a key from `JWT_SECRET`), so a token rotated less than `auth.RefreshReuseGrace` (60 s, RFC 9700's short leeway for a lost Set-Cookie) ago (racing tabs, a lost response) gets an access token for its family and the same successor cookie again while that is still the family's live token — never a second rotation; rotated longer ago (in a live family) is reuse: every family revoked + token_version bumped + `SESSION_REVOKED` in that TX (`Tx.revokeUser`, shared with logout), warning logged (never the token), 401 with the cookie cleared; expiry (idle or family) is checked before rotation and revocation, so an expired token — rotated or not — and a token of a revoked family are just 401 (revoking again for a stale cookie would let it sign the user out over and over). A login replacing the browser's family takes that family's user lock before revoking it, like refresh and logout. Every session time and verdict (created/expires/family expiry, rotated_at, revoked_at, the grace and expiry checks, `SessionUser`, the purge) is the **database clock** (`clock_timestamp()`, read once per refresh after its locks; `now()` only where an index needs a stable value), never an API instance's, so drifting replicas agree; the store returns the times the handler needs (`Session.IssuedAt`, `RefreshResult.Now` → cookie Max-Age). Only the JWT's `exp` is on the instance clock (`TestSessionVerdictsUseTheDatabaseClock`). Cookie-only requests (refresh, logout without Bearer) pass `cookieGuard`: `Origin`, when sent, is the request's own (scheme from `X-Forwarded-Proto` only when the peer is in `TRUSTED_PROXIES`) or in `ALLOWED_ORIGINS`, and `X-Requested-With: fetch` is required (never added to CORS Allow-Headers); login/register check `Origin` too and take only `Content-Type: application/json` (400 otherwise: no forged form body), and every auth write refuses `Sec-Fetch-Site: cross-site` (403). Access tokens and WS tickets carry `sid`: `requireAuth` and WS open need the family live (not revoked, before its end; `store.FindUserSession` reads it with the user in one query, cached per instance next to the user for `USER_CACHE_TTL`, `httpapi.familyCache`), and the hub's sweep checks it for every socket in its batched round trip (`store.FindUsersAndSessions`), so a family revoked by a replacing login ends its access tokens and sockets too. Cookie-only logout spends the refresh per-IP budget; `/auth/ws-ticket` answers `Cache-Control: no-store`. Refresh is throttled per client IP (`REFRESH_LIMIT_PER_IP`, fail-open); the maintenance purge deletes rows of ended families or a day past their idle expiry (`Store.PurgeAuthSessions`). Tokens carry `users.token_version`; `requireAuth` and WS open check it, logout (Bearer or live cookie) bumps it, revokes every refresh family, and emits `SESSION_REVOKED` (outbox) carrying the new version, so every hub closes that user's sockets opened with an older version (`Event.TokenVersion`; 0 = all) — a replayed or late revoke never closes a newer session; a hub holds at most 10 sockets per user (`SetMaxConnsPerUser`: a handshake over the cap gets HTTP 429 + `Retry-After` without upgrading, so browsers do not see an open socket and reconnect at once; `register` re-checks under the lock and closes a racing one with 1013; both count in `RejectedConnections`; a revoke is also remembered per user for 2 min (bounded, `Hub.revoked`: version floor, or for version 0 the revoke time vs the handshake's accept time), so a handshake that read the user before the logout but registers after the `SESSION_REVOKED` is closed at `register` with 1008, not left to the sweep; `closeUser` touches only that user's sockets (per-user index)); a per-hub sweep (about once per ping period, jittered) re-checks active/role/customer/dealership/version and the socket's refresh family for every open socket in one batched round trip (`store.FindUsersAndSessions`) and closes mismatches. WS tickets are single-use (Redis `SETNX` on the `jti`, fail-open when Redis is down), burned only after every other handshake check passed (a 503 reading the user or a bad filter leaves the ticket for the retry). Redis is optional at startup too: unreachable is a warning and readiness reports `degraded` (`REDIS_REQUIRED=true` makes it fatal), so a Redis outage during a restart never becomes an API outage. Every Redis call's bound relies on `cache.New` setting go-redis `ContextTimeoutEnabled` (otherwise context deadlines are ignored and a Redis that accepts but never answers stalls each request for the client's multi-second read timeout — `TestFastPathHonoursItsBudgetWhenRedisHangs`); readiness probes Redis concurrently with Postgres under its own 250 ms budget. The shared rate limiter also fails open, except `login:`/`register:` buckets, which then count in a bounded per-instance memory limiter (`httpapi.memoryLimiter`); a request's throttle cost is one `INCRBY` of `cache.Bucket.Cost` per bucket. `requireAuth` reads the user through a per-instance cache (`httpapi.WithUserCache`, `USER_CACHE_TTL`, default 5 s, bounded; the token-version check runs on the cached row), so a change made elsewhere (another instance, SQL) applies within that TTL — logout on the serving instance and `Server.InvalidateUser` (wired to `SESSION_REVOKED`) apply at once; WS open always reads fresh, and only staff may open a socket with a Bearer token (customers use tickets). A socket's session expiry is the token's `sexp` (family absolute end, copied onto tickets), not the access token's `exp`: sockets outlive the 15 min access token and still close on revocation through token_version.
16. **Config changes never strand bookings**: dealership hours/lunch, weekday overrides, closures (all lock the dealership row `FOR UPDATE`, bump its version, and share `Tx.refuseStranded` — like the roster guard, over the part still ahead of now of every confirmed or checked-in appointment not yet ended, so a started job is never stranded and an edit touching only a window's past is allowed), technician shifts/absences (lock the technician `FOR UPDATE`, bump its version, `Tx.refuseStrandedTechnician` — over the part still ahead of now of every confirmed or checked-in appointment; in-progress work is left out, so an overrun on the lift never blocks roster edits) and technician deactivation/skill-level downgrades (checked against the booked `min_skill_level`, over every hold not yet ended) and skill removals (`PATCH /admin/technicians/:id` `skills` is the full set; refused while a hold not yet ended has a booked `required_skills` entry outside it; the technician row is locked `FOR UPDATE` first, so it serialises with `LockBookableTechnician`, which reads skills after its `FOR SHARE`) return 409 while upcoming appointments depend on them; "now" in all of these checks is the `booking.Service` clock passed as a `timestamptz` parameter, never Postgres `now()`, so a pinned test clock is deterministic; service-type changes apply to new bookings only (best-effort guardrail, outside any TX: a PATCHed duration that no open weekday at any dealership can hold without crossing lunch is rejected; later hour changes are not re-checked).
17. **Overruns**: the maintenance sweeper auto-extends in-progress work past `end_at` (`OVERRUN_EXTEND_STEP`, ≤ `MaxExtend` past the booked labour time). When GiST blocks a whole step or the cap is reached it still extends as far as it goes (up to the next hold of the bay, technician, or vehicle — `Tx.FirstHoldAfter` — or the cap; `Tx.ExtendEndFlagged` keeps the flag), sets `overrun_at` and emits `APPOINTMENT_OVERRUNNING` once; while flagged, the job holds its bay and technician until it is completed (a carry-over, across days) for allocation and availability (rule 11; the flagging sweep queues with its start day's writers only, so for later days the hold is a pre-check and GiST stays the guarantee); flagged jobs stay in the sweep, so the extension resumes as soon as the next booking moves — **keeping** the flag (still overrunning, alerted once, still holding its bay and technician); only Complete, or a manual extend whose new end is ahead of now, clears it (an extension still ending in the past keeps it). Only flagged jobs already extended to the cap are left out of `Store.OverrunCandidates` (the sweep can do nothing more for them, and picking them every tick would starve the batch); a flagged job whose next whole step would pass the cap still comes through once to be extended up to it, and unflagged jobs at the cap still come through once to be flagged. Each job is then locked (`Tx.LockOverrun`, `SKIP LOCKED`, re-checked) and handled in a TX of its own with a 500 ms `lock_timeout` (`Tx.SetLockTimeout`, before any savepoint): an extension waiting on a booking still in flight gives up and is retried next tick (neither extended nor flagged), and a dispatcher completing one job never waits behind the rest of the batch. Every maintenance task (`worker.Maintenance` Tick/Purge) runs under a panic guard; a panicking task is logged and the rest still run. Lease reclaims run on every instance each tick; the sweeps (reminders at most every `ReminderEvery`, 1 min; no-shows; overruns) and the purges run on the one instance that wins the round's session advisory lock (`Store.WithTryLock`, `worker.sweepLock`) — only a cost saving, the SQL stays safe to run concurrently.
18. **Notifications** (`internal/notify`): producers only enqueue into `notifications` with a `dedupe_key` (Kafka event id per channel; reminders `kind|appointment|start|scheduled_at` — `scheduled_at` changes only on book/move, so a reassign never re-reminds; `notifications_reminder_slot_uniq` allows one non-skipped reminder per appointment + kind + slot + channel. A job moved A → B → A gets a fresh A reminder only if the first was skipped (still unsent when it left A) and the move back is still ahead of the reminder's lead time (`MinLead` counts from the latest move); an A reminder already sent is not repeated), so at-least-once delivery never double-sends; the sender leases rows (`SKIP LOCKED`, `claimed_at`), and reminders are deduplicated and skipped **by slot** (`notifications.start_at` vs the appointment's current `start_at`), never by timestamps — a reschedule committing mid-sweep must neither send the old time nor suppress the new one. Change notices carry `appointment_version`: a `rescheduled` notice is stale once a newer notice exists for the same appointment + channel, and any notice is stale once a newer one is already `sending`/`sent` (late redelivery); a notice waits while an older one is `sending`, or `pending` and not a superseded `rescheduled` — so a confirmation then a cancellation both go out in order, a burst of moves sends only the last, and the newest is always delivered. The stale predicate is part of the claim itself (the skip UPDATE is bookkeeping: only the oldest 4×limit due pending rows (`staleSkipWindow`), `LIMIT`, `SKIP LOCKED`; a stale row behind that window stays pending, never claimed, until the window reaches it) and is re-checked right before `Send` (`SkipStaleNotifications`, which shutdown does not interrupt). For the newer notices queued behind a head, `next_attempt_at` is only a cost hint that keeps them out of the claim's scan, like the outbox's: the claim holds back the never-claimed newer notices of each head it claims (`store.NotificationInflightHold`), a head that backs off pushes them up to its own retry time (never down), and a head that resolves (sent, failed, skipped before sending) releases them; only rows with `attempts = 0` are ever moved, so no row's own backoff changes (`TestBlockedNoticesLeaveTheClaimScan`). Finished rows are purged once both `created_at` and `start_at` are older than 30 days (> Kafka retention, so a replay still dedupes). In-progress work does not block roster edits. Customer PII stays server-side (logs mask recipients). `customers.name` / `users.name` must contain a non-space character (`*_name_not_blank`, `001_schema.sql`), and greetings never index into an empty name.
19. **Database waits are bounded**: the pool sets `lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout` (`store.ConfigurePool`), and every request (except `/metrics`; `/ws/dispatch` bounds only its handshake, `authenticateWSWithin`) carries a deadline, `REQUEST_TIMEOUT` (default 20 s, `httpapi.WithRequestTimeout`), which bounds pool acquire plus all its statements; config refuses `DB_STATEMENT_TIMEOUT >= REQUEST_TIMEOUT` and `REQUEST_TIMEOUT >= config.HTTPWriteTimeout` (30 s), and the gateway's `/api/` proxy timeout (35 s) stays above both. Timeouts and an expired request deadline map to 503 `busy` + `Retry-After` (`Tx.Commit` runs detached from the request's cancellation, bounded by 5 s, so the deadline cuts every wait before COMMIT but never reports failure for a write it lets commit; a write cut off just before COMMIT may still be retried safely: retries replay through Idempotency-Key / If-Match). The HTTP drain at shutdown is `REQUEST_TIMEOUT` + 1 s, capped at the background drain budget (`httpShutdownBudget`). A client that disconnects gets 499 with no body, logged at Debug, booking metric `canceled`, never a 500. Migrations clear them for their own session/TX.

## Code conventions

- Layering: `httpapi` (gin handlers) → `booking.Service` → `store` (raw pgx SQL, parameterized only, no ORM).
- Errors crossing to HTTP are `domain.NewError(domain.Code…, msg)`; `httpapi.fail` maps code → status (`invalid` 400, `not_found` 404, `conflict` 409, `unavailable` 422, `unauthorized` 401, `forbidden` 403, `precondition_failed` 412, `precondition_required` 428, `rate_limited` 429, `busy` 503). Unknown errors log and return 500 without leaking details — unless the request context ended: client gone is 499, the request deadline is 503 `busy`. CHECK violations become 400 with a readable message from `store.checkMessages` (the constraint name is only logged; add a message there for any new client-reachable CHECK).
- Handlers decode with `s.bindJSON` (exactly one JSON value: unknown fields and trailing data → 400; over 1 MiB → 413 `too_large`, written directly — the only code outside `domain`) and parse IDs with `s.pathUUID` / `s.queryUUID`.
- Responses are compressed in the backend, not at the gateway: `Server.Handler()` = `withCompression(engine())` (`httpapi/compress.go`, klauspost `gzhttp`: zstd, else gzip, bodies ≥ 1 KiB, `Vary: Accept-Encoding`, the ETag passed through unchanged). nginx would weaken the strong ETag (`"3"` → `W/"3"`) that `If-Match` needs, so never enable `gzip` for `/api/` in `deploy/gateway`. `/api/v1/auth/` (tokens: BREACH), `/api/v1/ws/` (upgrade) and `/metrics` (promhttp compresses itself) stay uncompressed (`uncompressed`); a new endpoint whose body carries a secret goes under `/api/v1/auth/` or into that list. Tests that check headers or encoding go through `Handler()`, not `engine()`.
- Every list endpoint is a keyset page (`store/page.go`: `LIMIT n+1` over a stable, unique order ending with the id, `WHERE (keys…, id) > (cursor values…)`, backed by an index the store explain test checks; never OFFSET, never a cursor row looked up by id) with the shared token and response convention of `httpapi/cursor.go` (plain array body, `X-Next-Cursor`, `limit`/`cursor`; a token is bound to its listing and filters). Scope filters apply before the keyset. A single-object read stays unpaged only when bounded by design (calendar closures, roster absences: capped at insert).
- Migrations in `internal/migrate/migrations/NNN_name.sql` are embedded and applied once by filename; the history was squashed into `001_schema.sql` before the first release, and `migrate.Up` refuses a database built by another migration layout (recreate it: `./scripts/up.sh`). **Never edit an existing migration** — add the next number (enforced by `scripts/check-migrations.sh`: `lint.sh` locally, the CI `migrations` job on PRs/pushes).
- `ctx` flows from the request through service and store; no `context.Background()` inside request paths.
- Tests: table-driven units next to code; DB tests in `internal/integration` (need `TEST_DATABASE_URL`). Any change to allocation/booking needs a concurrent test proving exactly one winner, and must pass `go test -race ./...` (CI runs the whole module, integration included, under `-race`).
